# Version Bump Checklist

This document answers one specific question:

- when cutting a new release, which files do you update manually
- which files are generated or rewritten by scripts

Use this together with:

- `docs/release-process.md` for the CLI/core release flow
- `docs/desktop/release.md` for the desktop release flow

## Release Types

This repo currently has two release tracks:

- CLI/core release tag: `v<version>`
- desktop release tag: `desktop-v<version>`

They do not use the same version source of truth.

## CLI/Core Release

Source of truth:

- `Directory.Build.props`

Manual update required:

- `Directory.Build.props`
  - update `<VersionPrefix>`

Current example:

- `Directory.Build.props` -> `0.0.6`

Do not manually edit these for a normal CLI/core release:

- `packaging/npm/clawsharp/package.json`
- `packaging/npm/@clawsharp/cli-win32-x64/package.json`
- `packaging/npm/@clawsharp/cli-win32-arm64/package.json`
- `packaging/npm/@clawsharp/cli-linux-x64/package.json`
- `packaging/npm/@clawsharp/cli-linux-arm64/package.json`
- `packaging/npm/@clawsharp/cli-darwin-x64/package.json`
- `packaging/npm/@clawsharp/cli-darwin-arm64/package.json`

Why:

- those package templates intentionally stay at `0.0.0-development` in git
- `eng/stage-npm-packages.ps1` rewrites them to the real release version when staging npm artifacts

Generated or script-written outputs for CLI/core release:

- `artifacts/release/`
- `artifacts/npm/`
- release archives uploaded by `.github/workflows/release.yml`

CLI/core version bump steps:

1. update `Directory.Build.props`
2. run local validation
3. commit
4. tag `v<version>`
5. push the tag

## Desktop Release

Desktop versioning is stricter because three files must stay in sync.

Manual source-of-truth files:

- `apps/desktop/package.json`
- `apps/desktop/src-tauri/tauri.conf.json`
- `apps/desktop/src-tauri/Cargo.toml`

All three must contain the same version.

Current example:

- `apps/desktop/package.json` -> `0.0.5`
- `apps/desktop/src-tauri/tauri.conf.json` -> `0.0.5`
- `apps/desktop/src-tauri/Cargo.toml` -> `0.0.5`

Validation:

- `eng/desktop-release-tools.mjs` checks that these three files match
- desktop release tags must match the same version, for example `desktop-v0.0.5`

Do not manually edit these as part of the normal desktop version bump:

- `apps/desktop/src-tauri/tauri.release.conf.json`
  - generated by release tooling
- `artifacts/desktop/release/`
- `artifacts/desktop/winget/`
- generated Homebrew cask output
- copied sidecar binaries under `apps/desktop/src-tauri/binaries/`

Lockfiles are not version sources of truth:

- `apps/desktop/package-lock.json`
- `apps/desktop/src-tauri/Cargo.lock`

If they change because npm or cargo rewrites them during a release-prep workflow, review and commit them if needed, but do not hand-edit them as the primary version bump step.

Desktop version bump steps:

1. update `apps/desktop/package.json`
2. update `apps/desktop/src-tauri/tauri.conf.json`
3. update `apps/desktop/src-tauri/Cargo.toml`
4. validate that all three match
5. commit
6. tag `desktop-v<version>`
7. push the tag

## Quick Reference

Manual files to update for `v<version>`:

- `Directory.Build.props`

Manual files to update for `desktop-v<version>`:

- `apps/desktop/package.json`
- `apps/desktop/src-tauri/tauri.conf.json`
- `apps/desktop/src-tauri/Cargo.toml`

Files intentionally rewritten by scripts:

- `packaging/npm/**/package.json`
- `apps/desktop/src-tauri/tauri.release.conf.json`
- `artifacts/**`

## Recommended Checks

CLI/core:

```bash
dotnet build ClawSharp.sln -c Release
dotnet test ClawSharp.sln -c Release
```

Desktop:

```bash
node eng/desktop-release-tools.mjs validate-version --tag desktop-v0.0.5
npm --prefix apps/desktop test
```

Replace the sample version with the version you are releasing.
